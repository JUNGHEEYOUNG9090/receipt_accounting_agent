# receipt_accounting_agent

영수증 이미지를 OCR과 Vision으로 분석하고, LLM을 통해 영수증 정보를 구조화한 뒤 LangGraph를 이용해 지출 카테고리를 분류하는 가계부 서비스입니다.

실제 영수증 35장을 대상으로 OCR, LLM, Vision 결과를 비교하고 Ground Truth를 기반으로 오류를 확인했습니다.

이후 Supabase를 이용한 영수증/품목 데이터 관리와 LangGraph 기반 카테고리 분류 Workflow를 구축하고, 사용자가 AI 분석 결과를 직접 검수하고 수정할 수 있는 가계부 UI까지 구현했습니다.

---

# 1. 프로젝트 개요

## 프로젝트 목표

영수증 분석 과정에서 발생하는 OCR 및 Vision의 한계를 확인하고, AI가 생성한 결과를 실제 가계부 서비스에서 사용할 수 있도록 다음 과정을 구현했습니다.

```text
영수증 이미지
    ↓
OCR / Vision 분석
    ↓
LLM 구조화
    ↓
Ground Truth와 결과 비교
    ↓
영수증 / 품목 데이터 저장
    ↓
LangGraph 카테고리 분류
    ↓
사용자 검수 및 수정
    ↓
가계부 데이터
```

단순히 AI 모델의 결과를 출력하는 것이 아니라,

- AI 결과를 구조화하고
- DB에 저장하고
- 이미 처리된 데이터는 재사용하고
- 필요한 경우에만 AI를 호출하고
- 사용자가 최종 결과를 직접 수정할 수 있도록

전체 Workflow를 구현하는 것을 목표로 했습니다.

```text

   │
   │ HTTP
```

- 공급가액
- 부가세
- 합계금액

- 수량
- 단가
- 금액

# 5. Vision 분석

영수증 이미지를 OpenAI Vision에 직접 전달하여 영수증 정보를 추출했습니다.

Vision 결과 역시 동일한 영수증의 Ground Truth와 비교했습니다.

OCR 기반 분석과 별도의 Vision 분석 경로를 구성함으로써 동일한 영수증을 서로 다른 방식으로 분석하고 결과 차이를 확인할 수 있도록 했습니다.

# 6. OCR / LLM / Vision 비교

AI 분석 기능은 실제 영수증을 이용해 테스트를 완료했습니다.

## 테스트 데이터

총 **35장의 실제 영수증**을 사용했습니다.

각 영수증에 대해 다음 데이터를 준비했습니다.

```text
실제 영수증
    ↓
Ground Truth

      ↙       ↘
OCR → LLM     Vision
      ↘       ↙
       결과 비교
```

---

## 6-1. OCR 결과

35장의 영수증을 대상으로 OCR을 수행했습니다.

- 성공: **35 / 35**
- 총 처리 시간: **약 1,157.91초**
- 약 **19분 18초**
- 5장씩 7개 배치 처리

OCR 자체는 모든 영수증에서 결과를 반환했습니다.

다만 상품명이나 일부 문자에서 오인식이 발생했으며, 영수증 촬영 방향이나 조명에 따라 인식 결과가 달라지는 경우가 확인되었습니다.

---

## 6-2. LLM 결과

OCR 결과를 LLM에 전달하여 구조화된 영수증 데이터를 생성했습니다.

초기 실행 결과:

- 성공: **31 / 35**

실패한 데이터만 재처리하여 최종적으로:

- 성공: **35 / 35**

모든 테스트 영수증에 대해 구조화 결과를 확보했습니다.

---

## 6-3. Vision 결과

Vision 모델을 이용해 동일한 35장의 영수증을 직접 분석했습니다.

초기 실행 결과:

- 성공: **30 / 35**

실패한 데이터만 재처리하여 최종적으로:

- 성공: **35 / 35**

Vision 역시 모든 테스트 데이터를 처리할 수 있도록 결과를 확보했습니다.

# 9. AI 분석 과정에서 확인한 한계

실제 영수증 35장을 사용하면서 AI 분석 과정에서 발생할 수 있는 오류를 확인했습니다.

## OCR

- 촬영 방향에 따른 인식 차이
- 조명 및 반사 영향
- 일부 상품명 오인식
- 숫자 오인식
- 영수증 형태에 따른 인식 품질 차이

## LLM

- OCR 결과가 잘못되었을 경우 구조화 결과에도 영향을 받을 수 있음
- 일부 실행에서 구조화 실패 발생
- 동일한 입력이라도 후처리 조건에 따라 재처리가 필요한 경우 발생

## Vision

- 상품명 오인식
- 일부 금액 정보 오류
- 영수증에 표시된 정보를 잘못 해석하는 경우 발생

따라서 AI 결과를 그대로 최종 데이터로 확정하지 않고 사용자가 확인하고 수정할 수 있는 구조를 구현했습니다.

# 11. LangGraph Workflow

LangGraph는 영수증 분석 결과의 정확도를 판단하는 용도가 아니라 **지출 카테고리 분류 과정의 Workflow를 관리하는 용도**로 사용했습니다.

현재 DB 상태에 따라 필요한 작업만 수행하도록 구성했습니다.

```text
START
  ↓
영수증 조회
  ↓
DB 상태 확인
  ↓
이미 분류됨?
  ├─ YES → 기존 결과 재사용
  │           ↓
  │       결과 구성
  │
  └─ NO
       ↓
    품목 존재?
       ├─ YES → 품목 카테고리 분류
       │           ↓
       │       결과 구성
       │
       └─ NO → 영수증 카테고리 분류
                   ↓
               결과 구성
                   ↓
                  END
```

---

# 12. 기존 분류 결과 재사용

이미 DB에 카테고리가 존재하는 경우 OpenAI를 다시 호출하지 않습니다.

예를 들어 영수증의 카테고리가 이미 저장되어 있다면 기존 결과를 그대로 사용합니다.

품목이 있는 영수증의 경우에도 모든 품목의 카테고리가 이미 존재하면 추가적인 AI 호출 없이 기존 결과를 사용합니다.

이를 통해 불필요한 LLM 호출을 줄이고 이미 처리된 데이터를 재사용할 수 있도록 구성했습니다.

# 14. 영수증 수정 API

영수증과 품목을 수정할 수 있도록 PATCH API를 구현했습니다.

```http
PATCH /receipts/{receipt_id}
```

## 영수증 수정

- 가맹점명
- 거래일시
- 공급가액
- 부가세
- 합계금액
- 할인금액

## 품목 수정

- 상품명
- 수량
- 단가
- 금액
- 카테고리

기존 품목은 UPDATE하고 새로 추가된 품목은 INSERT하도록 구현했습니다.

삭제된 품목은 DB에서도 삭제됩니다.

# 17. 카테고리별 가계부 UI

같은 날짜에 동일한 카테고리의 영수증이 여러 개 존재하더라도 하나의 카테고리로 묶어서 표시하도록 UI를 구성했습니다.

```text
2026-09-29

▼ 의류                       107,820원
  │
  ├─ 영수증 A
  │   ├─ 가게명
  │   ├─ 품목 A
  │   └─ 품목 B
  │
  └─ 영수증 B
      ├─ 가게명
      ├─ 품목 C
      └─ 품목 D

▼ 식료품                      65,260원
  │
  └─ 영수증 C
      ├─ 가게명
      ├─ 품목 E
      └─ 품목 F
```

카테고리 금액은 해당 카테고리에 포함된 품목 금액을 합산해서 표시합니다.

동일 카테고리의 영수증을 화면에서 묶어 보여주지만 DB의 영수증 데이터를 하나로 합치지는 않습니다.

각 영수증의 `receiptId`를 유지하기 때문에 개별 영수증 단위의 수정 및 삭제가 가능합니다.

# 18. 아이템 추가 처리

사용자가 가계부 화면에서 새로운 품목을 추가할 수 있습니다.

새 품목은 DB에 아직 `id`가 존재하지 않기 때문에 저장 시 기존 품목 UPDATE와 구분하여 INSERT합니다.

```text
기존 품목
id 있음
  ↓
UPDATE

새 품목
id 없음
  ↓
INSERT
```

이 과정에서 새 품목의 DB 저장 오류가 발생했던 문제를 수정했습니다.

# 22. 프로젝트에서 확인한 핵심 내용

실제 영수증을 대상으로 테스트하면서 AI가 영수증의 모든 정보를 항상 정확하게 추출하는 것은 아니라는 점을 확인했습니다.

따라서 현재 서비스는 다음과 같은 구조를 사용합니다.

```text
AI
 ↓
초기 데이터 생성
 ↓
DB
 ↓
사용자 검수
 ↓
수정
 ↓
최종 가계부 데이터
```

AI를 최종 결정자로 두기보다 **초기 데이터 생성과 분류를 자동화하고, 사용자가 최종 데이터를 확정할 수 있도록 하는 구조**입니다.

또한 LangGraph는 단순히 여러 LLM을 연결하는 용도가 아니라 DB 상태에 따라 이미 처리된 데이터는 재사용하고 필요한 경우에만 분류를 수행하는 Workflow 관리에 사용했습니다.
