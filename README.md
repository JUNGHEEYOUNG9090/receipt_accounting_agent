# Receipt Accounting Agent

영수증 이미지를 기반으로 상품 정보를 추출하고, AI를 활용해 지출 항목을 자동으로 분류하는 **AI 기반 영수증 가계부 서비스**입니다.

OCR 및 Vision 모델을 활용해 영수증 데이터를 구조화하고, 추후 LangGraph를 이용해 **검증 → 재처리 → 사용자 확인** 등의 처리 흐름을 관리하는 것을 목표로 합니다.

사용자가 최종 결과를 직접 확인하고 수정할 수 있도록 하여 OCR 및 AI 모델의 오류를 보완하는 것을 목표로 합니다.

---

## 프로젝트 소개

마트나 식자재 매장에서 장을 본 뒤 영수증을 확인하면 식품, 생활용품 등 서로 다른 종류의 상품이 하나의 영수증에 함께 포함되어 있습니다.

기존 가계부 서비스에서는 이러한 지출을 직접 분류해야 하는 경우가 많기 때문에,

> **영수증을 사진으로 찍으면 상품별로 자동 분류해주는 가계부**

를 목표로 프로젝트를 진행합니다.

현재는 다음과 같은 중분류를 기준으로 개발하고 있습니다.

```text
장바구니

├── 식비
├── 생활비
└── 기타
```

추후 실제 영수증 데이터를 확인한 후 필요에 따라 세부 분류를 추가할 예정입니다.

## 주요 기능

### 1. 영수증 이미지 업로드

사용자가 영수증 사진을 업로드하여 자동 분석을 시작할 수 있도록 구성합니다.

모바일 환경에서 사진을 촬영하거나 이미지를 선택할 수 있도록 반응형 UI로 개발합니다.

촬영 조건에 따라 인식 결과가 달라질 수 있기 때문에 **영수증을 세로 방향으로 촬영하는 것을 권장**합니다.

### 2. 영수증 OCR

기존에 구축한 OCR 서버를 활용하여 영수증 이미지에서 텍스트를 추출합니다.

```text
영수증 이미지
      ↓
PaddleOCR-VL v1.6
      ↓
OCR 결과
```

OCR 서버는 FastAPI와 Docker를 이용해 별도 서버로 구성했습니다.

여러 장의 영수증을 처리할 경우 5장 단위로 OCR 요청을 분할하여 처리하며, 각 배치의 결과를 JSON 파일로 저장합니다.

```text
35개 영수증
    ↓
5개씩 배치 처리
    ↓
ocr_results_batch_01.json
ocr_results_batch_02.json
...
ocr_results_batch_07.json
```

### 3. LLM 기반 데이터 구조화

OCR 결과를 OpenAI API를 이용해 분석하여 영수증 정보를 구조화된 JSON으로 변환합니다.

```text
OCR 결과
   ↓
OpenAI LLM
   ↓
구조화된 영수증 데이터
```

추출 항목:

- 가맹점명
- 거래일시
- 상품명
- 단가
- 수량
- 금액
- 공급가액
- 부가세
- 합계금액

LLM 처리 중 특정 영수증에서 오류가 발생하더라도 해당 영수증만 건너뛰고 나머지 영수증의 처리를 계속하도록 구성했습니다.

### 4. Vision 기반 데이터 추출

OCR 결과를 거치지 않고 영수증 이미지를 Vision 모델에 직접 전달하여 데이터를 추출하는 방식도 구현했습니다.

```text
영수증 이미지
      ↓
OpenAI Vision
      ↓
구조화된 영수증 데이터
```

OCR → LLM 방식과 동일한 영수증을 대상으로 비교하여 다음 항목을 확인합니다.

- 데이터 추출 정확도
- 상품 구조 인식
- 처리 시간
- API 비용
- 처리 실패 여부

### 5. 상품 카테고리 분류

추출된 상품을 지출 목적에 따라 분류합니다.

```text
농심)짜왕멀티 4입

→ 식비
```

```text
LG)샤프란핑크옹기 3.1L

→ 생활비
```

### 6. 사용자 수정

OCR 또는 AI 모델의 결과가 항상 정확하지 않을 수 있기 때문에 최종 저장 전에 사용자가 결과를 확인하고 수정할 수 있도록 구성합니다.

예:

```text
상품명

[ CJ)스팸라이트 120g ]

금액

[ 4,950원 ]

분류

[ 식비 ▼ ]

[ 수정 완료 ]
```

### 7. 지출 내역 저장

사용자가 최종 확인한 상품 및 분류 정보를 PostgreSQL/Supabase에 저장할 예정입니다.

## 현재 처리 구조

현재는 최종 Agent Workflow를 구현하기 전에 **OCR → LLM과 Vision 방식을 비교·검증하는 단계**입니다.

```text
                 영수증 이미지
                      │
             ┌────────┴────────┐
             ↓                 ↓
       PaddleOCR-VL       OpenAI Vision
             ↓                 ↓
         OCR 결과          Vision 결과
             ↓
        OpenAI LLM
             ↓
         LLM 결과
             │                 │
             └────────┬────────┘
                      ↓
                  결과 비교
                      ↓
                  정확도 검증
```

현재 테스트 데이터는 **35개의 실제 영수증 이미지**로 구성했습니다.

하이패스처럼 상품 목록이 존재하지 않는 영수증, 편의점·식당 등 다양한 형태의 영수증과 촬영 상태가 좋지 않은 영수증을 포함하여 실제 사용 환경에서 발생할 수 있는 오류도 확인하고 있습니다.

비교 항목:

- 상품명 인식
- 상품 개수 및 구조
- 가격 및 수량
- 공급가액 / 부가세 / 합계금액
- 처리 시간
- API 비용
- 처리 실패 여부

## LangGraph Workflow

현재 LangGraph를 이용해 OCR → LLM → Vision 전체 처리 파이프라인을 구성했습니다.

다음 단계에서는 단순히 모든 영수증에 Vision을 호출하는 방식에서 벗어나, **검증 결과에 따라 필요한 경우에만 재처리하는 Workflow**로 발전시킬 예정입니다.

최종 목표 구조:

```text
START
  ↓
영수증 분석
  ↓
상품 추출
  ↓
상품 분류
  ↓
검증
  ├── 정상 ─────→ 사용자 확인
  │
  └── 문제 있음
          ↓
        재처리
          ↓
        검증
          ↓
      사용자 확인
          ↓
         저장
          ↓
         END
```

예를 들어 OCR → LLM 과정에서 필수 정보가 누락되거나 결과 구조가 잘못된 경우 Vision을 fallback으로 호출하는 방식으로 구현할 예정입니다.

LangGraph에서는 영수증 처리 과정에서 공유되는 State와 각 처리 단계를 Node로 구성하고, 검증 결과에 따라 Conditional Edge를 이용해 다음 처리 경로를 결정하는 것을 목표로 합니다.

### 주요 개념

| 개념             | 역할                                 |
| ---------------- | ------------------------------------ |
| State            | 영수증 처리 과정에서 공유되는 데이터 |
| Node             | OCR, 추출, 분류, 검증 등의 개별 처리 |
| Edge             | 다음 처리 단계로 이동                |
| Conditional Edge | 검증 결과에 따른 분기                |
| Graph            | 전체 영수증 처리 Workflow            |

## OCR / LLM / Vision 비교

동일한 영수증을 대상으로 OCR → LLM 방식과 Vision 방식을 비교하고 있습니다.

### A. OCR 기반

```text
영수증 이미지
    ↓
PaddleOCR-VL
    ↓
OCR Text
    ↓
OpenAI LLM
    ↓
구조화 결과
```

### B. Vision 기반

```text
영수증 이미지
    ↓
OpenAI Vision
    ↓
구조화 결과
```

현재 35개 영수증을 대상으로 비교 테스트를 진행했습니다.

### 2026-09-26 테스트 결과

| 처리 단계 |    성공 | 실패 |
| --------- | ------: | ---: |
| OCR       | 35 / 35 |    0 |
| LLM       | 31 / 35 |    4 |
| Vision    | 30 / 35 |    5 |

OCR은 5장 단위의 7개 배치로 처리했으며, 모든 배치의 OCR 결과를 개별 JSON 파일로 저장했습니다.

```text
ocr_results_batch_01.json
ocr_results_batch_02.json
ocr_results_batch_03.json
ocr_results_batch_04.json
ocr_results_batch_05.json
ocr_results_batch_06.json
ocr_results_batch_07.json
```

### 확인된 실패 사례

`receipt_010.jpg`은 이미지 상태가 좋지 않아 OCR 결과에 한글과 문자열이 심하게 깨지는 현상이 발생했습니다.

```text
원본 이미지
    ↓
OCR 결과 심하게 훼손
    ↓
LLM JSON 구조화 실패
```

반면 동일한 영수증을 Vision에 전달했을 때는 주요 결제 정보와 가맹점 정보를 추출할 수 있었습니다.

이러한 사례를 통해 **OCR 결과의 품질이 후속 LLM 처리 결과에도 영향을 줄 수 있으며, Vision을 fallback으로 활용할 가능성**을 확인했습니다.

또한 `receipt_017.jpg`처럼 OCR과 LLM은 정상적으로 처리되었지만 Vision 단계에서 JSON 파싱 오류가 발생하는 경우도 확인했습니다.

따라서 단순히 특정 방식이 항상 우수하다고 판단하기보다는 Ground Truth를 기준으로 필드별 정확도와 실패 원인을 추가로 분석할 예정입니다.

## 오류 처리 및 결과 보존

여러 영수증을 한 번에 처리할 때 특정 영수증의 오류로 전체 작업이 중단되지 않도록 예외 처리를 적용했습니다.

```text
영수증 1 → 성공
영수증 2 → 성공
영수증 3 → 오류 → 건너뜀
영수증 4 → 성공
영수증 5 → 성공
```

또한 OCR은 5장 단위로 처리한 뒤 각 배치의 결과를 즉시 JSON 파일로 저장합니다.

따라서 후속 LLM 또는 Vision 단계에서 오류가 발생하더라도 이미 완료된 OCR 결과를 보존할 수 있습니다.

향후에는 저장된 OCR 결과를 이용해 **OCR을 다시 실행하지 않고 LLM / Vision 단계부터 재실행하는 기능**을 추가할 예정입니다.
