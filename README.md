# Receipt Accounting Agent

영수증 이미지를 기반으로 상품 및 결제 정보를 추출하고, **OCR과 Vision 기반 AI의 결과를 비교·검증하는 AI 영수증 데이터 추출 프로젝트**입니다.

기존에 구축한 PaddleOCR-VL 기반 OCR 서버와 OpenAI API를 활용하여 영수증 데이터를 구조화하고, 동일한 영수증에 대해 **OCR → LLM 방식과 Vision 방식을 비교**하여 정확도, 처리 시간, API 비용 및 오류 사례를 분석하는 것을 목표로 합니다.

최종적으로 검증된 영수증 데이터를 이후 가계부 서비스에서 활용할 수 있도록 데이터 추출 단계의 품질을 확인하는 것이 현재 프로젝트의 목적입니다.

---

## 프로젝트 소개

영수증에는 가맹점명, 거래일시, 상품명, 가격, 수량, 공급가액, 부가세, 합계금액 등 다양한 정보가 포함되어 있습니다.

하지만 실제 영수증은 매장마다 형식이 다르고, 촬영 상태에 따라 OCR 결과가 크게 달라질 수 있습니다.

따라서 본 프로젝트에서는 실제 영수증을 대상으로 여러 AI 처리 방식을 적용하고 결과를 비교합니다.

> **영수증 이미지를 AI로 분석하여 구조화된 데이터로 변환하고, 어떤 방식에서 어떤 오류가 발생하는지 검증하는 것**

을 주요 목표로 합니다.

현재 테스트 데이터는 **실제 영수증 35장**으로 구성되어 있습니다.

하이패스 충전 영수증, 편의점, 마트, 식당, 주유소, 약국 등 다양한 형태의 영수증을 포함하여 실제 사용 환경에서 발생할 수 있는 차이를 확인합니다.

---

## 프로젝트 범위

현재 프로젝트에서는 **영수증 데이터 추출과 비교 검증**에 집중합니다.

```text
영수증 이미지
      │
      ├───────────────┐
      ↓               ↓
PaddleOCR-VL      OpenAI Vision
      ↓               ↓
  OCR 결과        Vision 결과
      ↓
  OpenAI LLM
      ↓
  LLM 결과
      │               │
      └───────┬───────┘
              ↓
         결과 비교
              ↓
       Ground Truth 비교
              ↓
    정확도 / 시간 / 비용 분석
```

현재 프로젝트에서 확인하는 주요 항목:

* 영수증 정보 추출
* 상품 목록 구조화
* OCR → LLM 방식과 Vision 방식 비교
* 필드별 정확도
* 처리 시간
* API 비용
* 처리 실패 여부
* 오류 유형 분석

**LangGraph를 이용한 가계부 Workflow는 현재 프로젝트의 범위에 포함하지 않습니다.**

추후 별도의 가계부 프로젝트로 확장하면서 구조화된 영수증 데이터를 활용하고, 해당 단계에서 LangGraph를 적용할 예정입니다.

# 주요 기능

## 1. 영수증 이미지 업로드

사용자가 영수증 이미지를 업로드하여 분석할 수 있도록 구성합니다.

모바일 환경에서 사진을 촬영하거나 이미지를 선택할 수 있도록 반응형 UI로 개발합니다.

촬영 조건에 따라 OCR 결과가 달라질 수 있기 때문에 **영수증을 세로 방향으로 촬영하는 것을 권장**합니다.

---

## 2. 영수증 OCR

기존에 구축한 OCR 서버를 활용하여 영수증 이미지에서 텍스트를 추출합니다.

```text
영수증 이미지
      ↓
PaddleOCR-VL v1.6
      ↓
OCR Text
```

OCR 서버는 FastAPI와 Docker를 이용해 별도 서버로 구성했습니다.

35개의 영수증을 5장씩 나누어 처리하고, 각 배치의 결과를 JSON 파일로 저장했습니다.

```text
35개 영수증
    ↓
5개씩 배치 처리
    ↓
ocr_results_batch_01.json
ocr_results_batch_02.json
...
ocr_results_batch_07.json
```

OCR 결과에는 영수증별 OCR 텍스트와 처리 시간을 저장하여 이후 LLM 처리 및 성능 비교에 활용합니다.

---

## 3. OCR → LLM 데이터 구조화

OCR 결과를 OpenAI API에 전달하여 영수증 정보를 구조화된 JSON으로 변환합니다.

```text
OCR 결과
   ↓
OpenAI LLM
   ↓
구조화된 영수증 데이터
```

추출 항목:

* 가맹점명
* 거래일시
* 상품명
* 단가
* 수량
* 금액
* 공급가액
* 부가세
* 합계금액

LLM 프롬프트에는 OCR 결과의 위치와 문맥을 기준으로 상품명, 단가, 수량, 금액을 대응하도록 규칙을 적용했습니다.

또한 다음과 같은 예외 상황을 고려했습니다.

* 상품 목록이 없는 영수증
* 할인 및 행사 금액이 포함된 영수증
* 동일한 숫자가 여러 번 표시되는 영수증
* OCR 결과가 일부 훼손된 영수증
* 공급가액 / 부가세 / 합계금액이 함께 표시된 영수증

상품 목록을 확인할 수 없는 경우에는 상품을 임의로 생성하지 않고 `items: []`로 처리합니다.

---

## 4. Vision 기반 데이터 추출

OCR을 거치지 않고 영수증 이미지를 Vision 모델에 직접 전달하여 데이터를 추출합니다.

```text
영수증 이미지
      ↓
OpenAI Vision
      ↓
구조화된 영수증 데이터
```

Vision 결과 역시 OCR → LLM 방식과 동일한 JSON 구조를 사용합니다.

이를 통해 동일한 영수증을 대상으로 다음 항목을 비교합니다.

* 가맹점명
* 거래일시
* 상품명
* 단가
* 수량
* 금액
* 공급가액
* 부가세
* 합계금액

---

## 5. 결과 비교

동일한 영수증에 대해 다음 결과를 하나의 데이터셋에서 비교합니다.

```text
실제 영수증
    │
    ├── Ground Truth
    │
    ├── OCR
    │
    ├── LLM
    │
    └── Vision
```

비교 대상:

* 가맹점명 정확도
* 거래일시 정확도
* 상품명 정확도
* 상품 개수
* 단가
* 수량
* 상품별 금액
* 공급가액
* 부가세
* 합계금액

단순히 전체 성공/실패 여부만 확인하지 않고 **필드별 결과를 비교**하여 어떤 정보에서 오류가 발생하는지 확인합니다.

# OCR 처리 성능

35개 영수증을 5장씩 총 7개 배치로 처리했습니다.

```text
35개 영수증
    ↓
5개 단위 배치
    ↓
7개 OCR 요청
```

전체 OCR 처리 시간:

**약 1,157.91초 (약 19분 18초)**

처리 결과:

```text
OCR 성공: 35 / 35
OCR 실패: 0 / 35

총 처리 시간:
약 1,157.91초
약 19분 18초
```

각 배치의 결과를 별도 JSON으로 저장하여 후속 단계에서 오류가 발생해도 OCR을 다시 실행할 필요가 없도록 구성했습니다.

---

# 오류 처리 및 결과 보존

여러 영수증을 처리할 때 특정 영수증의 오류 때문에 전체 작업이 중단되지 않도록 개별 오류 처리를 적용했습니다.

```text
영수증 1 → 성공
영수증 2 → 성공
영수증 3 → 오류 → 건너뜀
영수증 4 → 성공
영수증 5 → 성공
```

또한 이미 성공한 결과를 보존하면서 실패한 영수증만 재처리할 수 있도록 결과 병합 방식을 적용했습니다.

예를 들어 Vision 처리에서 일부 영수증의 JSON 파싱 오류가 발생했을 때 전체 35개를 다시 호출하지 않고 실패한 영수증만 재호출한 뒤 기존 결과와 병합했습니다.

```text
기존 결과
    ↓
실패 영수증 확인
    ↓
실패 영수증만 재처리
    ↓
기존 결과와 병합
    ↓
최종 결과 파일
```

이를 통해 불필요한 API 호출을 줄이고 이미 처리된 결과를 보존할 수 있도록 했습니다.

# Ground Truth 및 데이터 정제

AI 모델의 결과를 비교하기 위해서는 실제 영수증의 값을 기준으로 결과를 검증해야 합니다.

따라서 35개 영수증의 실제 내용을 직접 확인하여 **Ground Truth(실제값)**를 정리했습니다.

비교 대상:

* 가맹점명
* 거래일시
* 상품명
* 단가
* 수량
* 금액
* 공급가액
* 부가세
* 합계금액

기존 백업 Excel에 실제값과 OCR 결과를 보존하고, 새롭게 생성한 비교 Excel에 LLM 및 Vision 결과를 추가하여 비교할 수 있도록 구성했습니다.

이를 통해 35개 영수증에 대한 비교 데이터 정제를 완료했습니다.

# 확인된 주요 사례

## 1. OCR 품질에 따른 후속 처리 영향

이미지 품질이 좋지 않은 영수증에서는 OCR 결과 자체가 심하게 훼손될 수 있음을 확인했습니다.

```text
원본 영수증
    ↓
OCR
    ↓
텍스트 훼손
    ↓
LLM 구조화 결과에 영향
```

이러한 사례를 통해 OCR 결과의 품질이 후속 데이터 구조화에 중요한 영향을 줄 수 있음을 확인했습니다.

---

## 2. Vision도 별도의 오류 처리가 필요

Vision 방식에서도 모델 응답이 예상한 JSON 형식으로 반환되지 않아 JSON 파싱 오류가 발생하는 사례가 있었습니다.

따라서 Vision 역시 단순히 이미지 입력만으로 항상 정상적인 결과를 보장하는 것은 아니며, 응답 검증과 예외 처리가 필요합니다.

---

## 3. 상품 목록이 없는 영수증

하이패스 충전과 같이 일반적인 상품 목록이 존재하지 않는 영수증도 확인했습니다.

이 경우 상품을 임의로 생성하지 않고 다음과 같이 처리합니다.

```json
{
  "items": []
}
```

---

## 4. 다양한 상품 수를 가진 영수증

상품이 적은 영수증뿐만 아니라 여러 상품이 포함된 마트 영수증도 테스트했습니다.

상품 수가 증가할수록 단순히 합계금액을 추출하는 것뿐 아니라 상품명, 단가, 수량, 금액의 대응 관계를 유지하는 것이 중요하기 때문에 상품 구조 인식 여부도 비교 대상으로 사용합니다.

# 향후 가계부 프로젝트

현재 Receipt Accounting Agent에서는 **영수증 데이터 추출과 모델 비교·검증**에 집중합니다.

이후 별도의 가계부 프로젝트로 확장하면서 본 프로젝트에서 검증된 영수증 데이터를 활용할 예정입니다.

```text
Receipt Accounting Agent
        │
        ↓
영수증 데이터 추출
        │
        ↓
검증된 구조화 데이터
        │
        ↓
────────────────────
        ↓
가계부 프로젝트
        ↓
상품 분류
        ↓
지출 관리
        ↓
LangGraph Workflow
```

가계부 프로젝트에서는 상품의 지출 목적을 분류하고, 필요한 경우 여러 처리 단계를 연결하기 위해 LangGraph를 활용하는 방향을 검토합니다.

따라서 **LangGraph는 현재 영수증 데이터 추출 프로젝트의 핵심 처리 도구가 아니라, 이후 가계부 서비스 단계에서 활용할 예정인 기술**입니다.

여러 영수증을 처리할 때 개별 영수증의 오류로 전체 작업이 중단되지 않도록 예외 처리를 적용했습니다.

## 4. 다양한 영수증 유형 테스트

마트, 편의점, 식당, 주유소, 약국, 하이패스 등 다양한 형태의 영수증을 테스트 데이터에 포함했습니다.

상품 목록이 존재하지 않는 영수증은 `items: []`로 처리하도록 데이터 구조를 정리했습니다.
