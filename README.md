# Receipt Accounting Agent

영수증 이미지를 기반으로 상품 및 결제 정보를 추출하고, **OCR과 Vision 기반 AI의 결과를 비교·검증하는 영수증 데이터 추출 프로젝트**다.

기존에 구축한 PaddleOCR-VL 기반 OCR 서버와 OpenAI API를 활용하여 영수증 데이터를 구조화하고, 동일한 영수증에 대해 **OCR → LLM 방식과 Vision 방식을 비교**하여 정확도, 처리 시간, API 비용 및 오류 사례를 분석했다.

또한 구조화된 영수증 데이터를 Supabase에 저장하고, **LangGraph를 이용하여 기존 분류 결과가 존재하는 경우 이를 재사용하고, 분류되지 않은 데이터에 대해서만 OpenAI를 호출하는 조건부 지출 카테고리 분류 Workflow**를 구현했다.

---

## 프로젝트 소개

영수증에는 가맹점명, 거래일시, 상품명, 가격, 수량, 공급가액, 부가세, 합계금액 등 다양한 정보가 포함되어 있다.

하지만 실제 영수증은 매장마다 형식이 다르고, 촬영 상태에 따라 OCR 결과가 크게 달라질 수 있다.

따라서 본 프로젝트에서는 실제 영수증을 대상으로 여러 AI 처리 방식을 적용하고 결과를 비교했다.

> **영수증 이미지를 AI로 분석하여 구조화된 데이터로 변환하고, 각 처리 방식에서 발생하는 오류와 성능 차이를 검증하는 것**

을 주요 목표로 했다.

현재 테스트 데이터는 **실제 영수증 35장**으로 구성되어 있다.

하이패스 충전 영수증, 편의점, 마트, 식당, 주유소, 약국 등 다양한 형태의 영수증을 포함하여 실제 사용 환경에서 발생할 수 있는 차이를 확인했다.

---

# 프로젝트 범위

현재 프로젝트는 크게 두 단계로 구성된다.

### 1. 영수증 데이터 추출 및 비교

```text
영수증 이미지

      │
      ├───────────────┐
      ↓               ↓

PaddleOCR-VL      OpenAI Vision

      ↓               ↓

 OCR 결과         Vision 결과

      ↓
 OpenAI LLM

      ↓
 LLM 결과

      │               │
      └───────┬───────┘
              ↓
        결과 비교
              ↓
       Ground Truth 비교
              ↓
     정확도 / 시간 / 비용 분석
```

### 2. 지출 카테고리 분류 Workflow

구조화된 영수증 데이터가 저장된 이후에는 LangGraph를 이용하여 분류 상태를 확인한다.

```text
영수증 데이터

      ↓

Supabase 조회

      ↓

기존 분류 결과 확인

      │
      ├── 이미 분류됨
      │       ↓
      │   기존 결과 재사용
      │       ↓
      │   OpenAI 호출 X
      │
      └── 미분류
              ↓
          OpenAI 호출
              ↓
          카테고리 추론
              ↓
          Supabase 저장
```

이를 통해 이미 처리된 데이터를 다시 AI에 전달하지 않고, 필요한 경우에만 OpenAI API를 호출하도록 구성했다.

# 주요 기능

## 1. 영수증 이미지 업로드

사용자가 영수증 이미지를 업로드하여 분석할 수 있도록 구성한다.

모바일 환경에서 사진을 촬영하거나 이미지를 선택할 수 있도록 반응형 UI를 적용하는 것을 목표로 한다.

촬영 조건에 따라 OCR 결과가 달라질 수 있기 때문에 **영수증을 세로 방향으로 촬영하는 것을 권장**한다.

---

## 2. 영수증 OCR

기존에 구축한 OCR 서버를 활용하여 영수증 이미지에서 텍스트를 추출했다.

```text
영수증 이미지
      ↓
PaddleOCR-VL v1.6
      ↓
OCR Text
```

OCR 서버는 FastAPI와 Docker를 이용해 별도 서버로 구성했다.

35개의 영수증을 5장씩 나누어 처리하고, 각 배치의 결과를 JSON 파일로 저장했다.

```text
35개 영수증

    ↓

5개씩 배치 처리

    ↓

ocr_results_batch_01.json
ocr_results_batch_02.json
...
ocr_results_batch_07.json
```

OCR 결과에는 영수증별 OCR 텍스트와 처리 시간을 저장하여 이후 LLM 처리 및 성능 비교에 활용했다.

---

## 3. OCR → LLM 데이터 구조화

OCR 결과를 OpenAI API에 전달하여 영수증 정보를 구조화된 JSON으로 변환했다.

```text
OCR 결과
   ↓
OpenAI LLM
   ↓
구조화된 영수증 데이터
```

추출 항목:

- 가맹점명
- 거래일시
- 상품명
- 단가
- 수량
- 금액
- 공급가액
- 부가세
- 합계금액

상품 목록을 확인할 수 없는 경우에는 상품을 임의로 생성하지 않고 `items: []`로 처리했다.

---

## 4. Vision 기반 데이터 추출

OCR을 거치지 않고 영수증 이미지를 Vision 모델에 직접 전달하여 데이터를 추출했다.

```text
영수증 이미지
      ↓
OpenAI Vision
      ↓
구조화된 영수증 데이터
```

Vision 결과 역시 OCR → LLM 방식과 동일한 JSON 구조를 사용했다.

이를 통해 동일한 영수증을 대상으로 다음 항목을 비교했다.

- 가맹점명
- 거래일시
- 상품명
- 단가
- 수량
- 금액
- 공급가액
- 부가세
- 합계금액

---

## 5. OCR / LLM / Vision 결과 비교

동일한 영수증에 대해 다음 결과를 하나의 데이터셋에서 비교했다.

```text
실제 영수증

    │
    ├── Ground Truth
    ├── OCR
    ├── LLM
    └── Vision
```

비교 대상:

- 가맹점명 정확도
- 거래일시 정확도
- 상품명 정확도
- 상품 개수
- 단가
- 수량
- 상품별 금액
- 공급가액
- 부가세
- 합계금액
- 처리 시간
- API 비용
- 처리 실패 여부

단순히 전체 성공/실패 여부만 확인하지 않고 **필드별 결과를 비교**하여 어떤 정보에서 오류가 발생하는지 확인했다.

---

## 6. LangGraph 기반 지출 카테고리 분류

구조화된 영수증 데이터를 Supabase에 저장한 후 지출 카테고리를 분류한다.

현재 카테고리는 다음 **13개 대분류**를 사용한다.

```text
식사
카페/음료
식료품
주유
교통
생활용품
위생용품
의류
문구/사무용품
철물/공구
의료/약품
담배
기타
```

현재는 세부적인 소분류는 적용하지 않고 대분류까지만 처리한다.

### 품목이 있는 영수증

```text
receipt_items 확인
      ↓
품목 category_id 확인
      │
      ├── 모든 품목이 이미 분류됨
      │       ↓
      │   기존 category_id 재사용
      │       ↓
      │   OpenAI 호출 X
      │
      └── 분류되지 않은 품목 존재
              ↓
          OpenAI 호출
              ↓
          품목별 카테고리 추론
              ↓
          receipt_items.category_id 저장
```

이후 품목의 분류 결과를 이용하여 영수증의 `receipts.category_id`도 저장한다.

혼합 카테고리 영수증의 경우 현재는 **가장 많이 등장한 카테고리**를 영수증의 대표 카테고리로 사용한다.

### 품목이 없는 영수증

```text
상품 정보 없음
      ↓
가맹점명 확인
      ↓
OpenAI
      ↓
카테고리 추론
      ↓
receipts.category_id 저장
```

### 이미 분류된 영수증

```text
receipts.category_id 존재
      ↓
기존 결과 사용
      ↓
OpenAI 호출 X
```

이를 통해 동일한 영수증을 반복 처리하더라도 이미 저장된 분류 결과를 다시 AI에 요청하지 않도록 구성했다.

# OCR 처리 성능

35개 영수증을 5장씩 총 7개 배치로 처리했다.

```text
35개 영수증
    ↓
5개 단위 배치
    ↓
7개 OCR 요청
```

전체 OCR 처리 시간:

**약 1,157.91초 (약 19분 18초)**

처리 결과:

```text
OCR 성공: 35 / 35
OCR 실패: 0 / 35

총 처리 시간:
약 1,157.91초
약 19분 18초
```

각 배치의 결과를 별도 JSON으로 저장하여 후속 단계에서 오류가 발생해도 OCR을 다시 실행할 필요가 없도록 구성했다.

---

# 오류 처리 및 결과 보존

여러 영수증을 처리할 때 특정 영수증의 오류 때문에 전체 작업이 중단되지 않도록 개별 오류 처리를 적용했다.

```text
영수증 1 → 성공
영수증 2 → 성공
영수증 3 → 오류 → 건너뜀
영수증 4 → 성공
영수증 5 → 성공
```

또한 이미 성공한 결과를 보존하면서 실패한 영수증만 재처리할 수 있도록 결과 병합 방식을 적용했다.

```text
기존 결과
    ↓
실패 영수증 확인
    ↓
실패 영수증만 재처리
    ↓
기존 결과와 병합
    ↓
최종 결과 파일
```

이를 통해 불필요한 API 호출을 줄이고 이미 처리된 결과를 보존할 수 있도록 구성했다.

# Ground Truth 및 데이터 정제

따라서 35개 영수증의 실제 내용을 직접 확인하여 **Ground Truth(실제값)**를 정리했다.

비교 대상:

- 가맹점명
- 거래일시
- 상품명
- 단가
- 수량
- 금액
- 공급가액
- 부가세
- 합계금액

이를 기준으로 OCR / LLM / Vision 결과를 비교할 수 있도록 데이터를 정제했다.

# 확인된 주요 사례

## 1. OCR 품질에 따른 후속 처리 영향

이미지 품질이 좋지 않은 영수증에서는 OCR 결과 자체가 심하게 훼손될 수 있음을 확인했다.

```text
원본 영수증
    ↓
OCR
    ↓
텍스트 훼손
    ↓
LLM 구조화 결과에 영향
```

---

## 2. Vision도 별도의 오류 처리가 필요

Vision 방식에서도 모델 응답이 예상한 JSON 형식으로 반환되지 않아 JSON 파싱 오류가 발생하는 사례가 있었다.

따라서 Vision 역시 응답 검증과 예외 처리가 필요한 것을 확인했다.

---

## 3. 상품 목록이 없는 영수증

하이패스 충전과 같이 일반적인 상품 목록이 존재하지 않는 영수증도 확인했다.

이 경우 상품을 임의로 생성하지 않고 다음과 같이 처리한다.

```json
{
  "items": []
}
```

---

## 4. 다양한 상품 수를 가진 영수증

상품이 적은 영수증뿐만 아니라 여러 상품이 포함된 마트 영수증도 테스트했다.

상품 수가 증가할수록 단순히 합계금액을 추출하는 것뿐 아니라 상품명, 단가, 수량, 금액의 대응 관계를 유지하는 것이 중요하기 때문에 상품 구조 인식 여부도 비교 대상으로 사용했다.

---

## 5. 기존 분류 결과 재사용

Supabase에 이미 품목별 또는 영수증별 카테고리가 저장되어 있는 경우 OpenAI를 다시 호출하지 않고 기존 결과를 사용하도록 구성했다.

```text
DB 확인

  ↓

category_id 존재?

  ├─ YES → 기존 결과 사용
  │         OpenAI 호출 X
  │
  └─ NO → OpenAI 호출
           ↓
       카테고리 추론
           ↓
         DB 저장
```

기존 데이터에 대해서도 해당 Workflow를 테스트했다.

`receipt_items.category_id`가 이미 존재하지만 `receipts.category_id`가 비어 있던 데이터에 대해 OpenAI를 호출하지 않고 기존 품목 분류 결과를 이용하여 영수증 카테고리를 저장하는 것을 확인했다.

또한 품목별 `category_id`가 정상적으로 저장되는 것도 확인했다.

# Vision 결과 사용자 검수

Vision을 이용해 영수증의 상품명, 수량, 금액, 결제금액 등을 추출하더라도 모든 영수증에서 정확한 결과를 보장할 수 없었다.

35개 영수증을 실제로 비교한 결과, 일부 영수증에서는 다음과 같은 오류가 확인됐다.

- 여러 상품이 하나의 상품명으로 합쳐지는 경우
- 상품명과 금액이 잘못 매칭되는 경우
- 수량이 누락되는 경우
- 할인 및 행사 항목이 누락되는 경우
- 상품별 금액은 잘못 인식되었지만 전체 결제금액은 일치하는 경우

예를 들어 상품이 여러 개 연속해서 표시되는 영수증에서는 Vision이 여러 상품을 하나의 품목으로 인식하는 문제가 발생했다.

따라서 Vision 결과를 별도의 검증 없이 바로 저장하지 않고, 사용자가 원본 영수증과 결과를 직접 확인할 수 있도록 **사용자 검수 단계**를 둔다.

```text
영수증 이미지
    ↓
Vision 분석
    ↓
AI 인식 결과 표시
    ↓
사용자 확인

    ├─ 정상 → 저장
    │
    └─ 오류 → 직접 수정
              ├─ 품목 수정
              ├─ 품목 추가
              ├─ 품목 삭제
              ├─ 수량 수정
              ├─ 금액 수정
              └─ 할인 항목 수정/추가

    ↓
저장 전 확인
    ↓
DB 저장
    ↓
LangGraph 카테고리 분류
```

화면에는 AI가 자동으로 인식한 결과임을 안내하고, 사용자가 원본 영수증과 한 번 확인하도록 한다.

> ⚠️ AI가 인식한 결과입니다. 정확한 기록을 위해 원본 영수증과 내용을 한 번 확인해주세요.

사용자가 결과를 수정한 경우에는 수정된 값을 최종 데이터로 저장한다.

저장 버튼을 누른 후에는 한 번 더 확인하도록 하여 사용자의 실수로 잘못된 데이터가 저장되는 것을 방지한다.

> 확인한 내용으로 저장하시겠습니까?

이를 통해 Vision의 인식 결과에만 의존하지 않고, **AI가 초안을 생성하고 사용자가 최종 데이터를 확정하는 방식**으로 서비스 구조를 설계한다.

# 실제 서비스 처리 흐름

현재까지 구현 및 검토한 전체 서비스 흐름은 다음과 같다.

```text
[영수증 업로드]
        ↓
[OCR / Vision 분석]
        ↓
[구조화된 영수증 데이터 생성]
        ↓
[사용자 검수 및 수정]
        ↓
[저장 확인]
        ↓
[Supabase 저장]
        ↓
[LangGraph 실행]
        ↓
[DB에 기존 카테고리 존재 여부 확인]
        ↓
   ┌────┴────┐
   ↓         ↓
이미 분류됨   미분류
   ↓         ↓
기존 값 재사용  OpenAI 분류
              ↓
            DB 저장
```

카테고리가 이미 DB에 존재하는 경우에는 OpenAI를 다시 호출하지 않고 기존 데이터를 재사용한다.

품목별 카테고리가 이미 저장되어 있는 경우에도 동일하게 기존 값을 활용하며, 필요한 경우에만 OpenAI를 호출하여 카테고리를 분류한다.

이를 통해 동일한 영수증 또는 이미 분류된 품목에 대해 불필요한 LLM 호출을 줄이고, 분류 결과를 지속적으로 재사용할 수 있도록 구성했다.

# 프로젝트에서 확인한 AI의 한계

이번 프로젝트에서는 OCR과 Vision을 실제 영수증 35장에 적용하면서 단순히 모델의 정확도만 확인하는 것이 아니라, **실제 서비스에서 AI 결과를 어떻게 사용할 것인지**까지 확인했다.

OCR은 이미지의 품질과 글자 인식 상태에 따라 오류가 발생할 수 있었고, Vision 역시 복잡한 영수증에서는 품목과 금액의 관계를 잘못 해석하거나 일부 항목을 누락하는 경우가 있었다.

특히 Vision 모델의 버전을 높이면 결과가 개선될 가능성은 있지만, 특정 모델이 모든 영수증에서 정확한 결과를 보장한다고 볼 수는 없다.

따라서 현재 프로젝트에서는 AI의 역할을 다음과 같이 구분했다.

- **OCR / Vision**: 영수증 데이터 자동 추출
- **사용자**: 추출 결과 최종 확인 및 수정
- **LangGraph + LLM**: 지출 카테고리 분류
- **Supabase**: 확정된 데이터 저장 및 기존 분류 결과 재사용

이를 통해 AI의 불확실성을 모델 자체의 개선에만 의존하지 않고 **사용자 검수와 서비스 Workflow를 통해 보완**하도록 구성했다.
